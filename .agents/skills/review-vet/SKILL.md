# 审查结论去伪存真 (Review Vet)

对输入的 Review 意见、代码评审或多轮审查反馈进行严格的合理性与真实性核验。以**代码事实**与**原始需求范围**为锚点，坚决遏制“用大词包装假需求、脱离实际加戏、过度工程及破坏性结论”。

## 核心流程

```
[输入 Review 结论]
       │
       ▼
1. 锚定基准 ─── 获取原任务需求/Issue/PRD + 检查相关代码事实与调用链路
       │
       ▼
2. 剥离与提纯 ─ 过滤大词修辞滤镜 + 解耦“真实痛点(Why)”与“过度方案(How)”
       │
       ▼
3. 四象限分流 ─ [采纳] 合理项 ｜ [超界] 需人工 ｜ [驳回] 伪需求 ｜ [存疑] 待裁决
       │
       ▼
4. 生成报告 ─── 输出去伪存真矩阵 + 事实证据反驳 + 建设性最小替代方案 + 人工决断清单
```

## 执行步骤

### 1. 锚定需求基准与代码事实 (Grounding)
- **需求锚点**：核对当前 Issue、PRD、Commit 记录或上下文。若无明确需求来源，主动询问或依据当前上下文设定基准范围。
- **事实锚点**：查看具体文件与代码行（禁止凭空脑补调用方或极端状态）。验证声称的“问题”是否能在真实链路中被触发。
- **契约基准**：核对 [AGENTS.md](../../AGENTS.md) 与项目 ADR（如单一主库、免 migration、禁止直接使用 semantic.raw.db 等硬性规则）。

### 2. 剥离大词与意图提纯 (Strip & De-couple)
- **去除大词滤镜**：无视“立足第一性原理”、“商业事实”、“极其破坏性”等修辞定性，只提取其具体的技术主张。
- **解耦 Why 与 How**：
  - 若其指出的**隐患真实**，但给出的**方案过度庞大**：驳回其方案，提纯其隐患，给出**最小可行防御补丁**。
  - 若隐患本身属于**脱离业务价值的假想敌**（攻防经济学不成立、违背现实物理算力或强实名法律成本）：彻底驳回。

### 3. 四象限严格分流 (Four-Quadrant Triage)
- **✅ 采纳 (In-Scope & Valid)**：在原需求范围内，有确切代码依据，修复真实 Bug/边界/安全问题。
- **⚠️ 超出范围 (Out-of-Scope)**：提出了原需求未包含的新特性或业务扩充。**严禁擅自实施，必须标出并请人工确认**。
- **❌ 驳回伪需求 (Bogus / Over-engineering)**：脱离代码链路凭空臆想、假大空扣帽子、违反项目契约、**脱离业务价值的假想敌过度防御**（如将几十元不可提现工具代币当千万加密货币防，假想攻击者盲猜 2^256 机器码并冒坐牢风险用强实名微信盗号）、过度设计。出具代码事实与攻防经济学证据予以驳回。
- **❓ 存疑权衡 (Ambiguous)**：设计取舍、利弊互现或信息不足项，列出权衡点交由人类决策。

### 4. 输出标准化审视报告
严格按照以下结构向用户汇报：
1. **审视裁决总览**（统计采纳/超界/驳回/存疑数量）
2. **逐项去伪存真矩阵**（条目、判定、代码证据、爆炸半径评估）
3. **针对伪需求与破坏性结论的澄清反驳**（摆事实，讲逻辑，给出建设性替代方案）
4. **待人工裁决清单**（超界与存疑项，提供明确选择支）
