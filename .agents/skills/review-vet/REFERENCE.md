# Review 去伪存真参考手册 (REFERENCE)

本手册提供在审视与辨识 Review 结论时的底层判定准则、典型伪需求特征库及反驳话术规范。

---

## 一、剥离修辞大词手册 (Strip the Rhetoric)

很多缺乏充分事实依据的 Review 意见，倾向于用“权威性、哲学化或极端性词汇”压制读者，制造紧迫感和权威假象。核验时必须**剥离情绪与修辞，提取实质命题**。

### 1. 常见修辞套路与透视对照表

| 表面修辞话术 | 真实透视逻辑 | 核验与审视动作 |
| :--- | :--- | :--- |
| *“立足于第一性原理，重新审视...”* | 往往掩盖缺乏具体上下文约束，试图从真空中推导宏大结论。 | 追问：其设定的“第一性假设”在当前业务中是否成立？是否有代码或 PRD 佐证？ |
| *“违背了 KISS 原则 / 过度设计”* | 常被滥用为偷懒、逃避必要错误处理或砍掉合理防御的借口。 | 检查：被批评的代码是为了真实边界场景还是凭空冗余？若有真实场景，则非过度。 |
| *“脱离本项目的真实商业事实”* | 审查者自封为商业代表，凭空捏造未曾定义的商业模式或计费逻辑。 | 检查：当前产品和任务定义中到底有没有该商业规则？若无，属于加戏伪需求。 |
| *“存在极其不合理甚至破坏性的结论”* | 用极端恐吓性定性夸大局部瑕疵，以此推销自己的全套方案。 | 检查：该破坏性在现有代码链路中真实发生的概率是多少？爆炸半径究竟多大？ |
| *“存在严重安全漏洞/机器码伪造/缺少签名鉴权/需要零信任体系”* | 将封闭、低价值、不可提现的单机软件代币当成几千万资金的加密货币冷热钱包；假想攻击者不仅能盲猜 2^256 物理机器码，还愿意冒着被抓风险用强实名微信焊死在账户上盗取几十块不可变现代币。 | 攻防经济学与误杀风险核验：核实资产真实价值与流动性；计算攻击者现实法律与算力成本；严查方案是否会因密钥失配导致真实用户严重误杀与客诉。若不成立，直接判定为假想敌过度工程驳回。 |
| *“防手误/防串号/需要用户二次确认/增加待确认状态”* | 为了 0.0001% 几乎不存在的极端手误，强行给 99.9999% 正常用户的核心转化链路制造阻碍；破坏付费后的即时满足感，凭空制造大量脆弱状态机与无效代码（pending_confirm、二次确认 RPC、解绑 RPC）。 | 转化漏斗与客服兜底核验：真实场景根本不存在串号动机（用户坐在电脑前用自己的微信扫码付款，充的就是当前物理机）；核心转化漏斗严禁增加阻断弹窗；十万分之一的极端偶发手误应由人工客服后台换绑兜底，严禁代码过度工程！ |

### 2. 命题提取三问
遇到任何充满修辞的结论，强制回答以下三问：
1. **主张是什么**：剔除形容词后，它要求改动哪一个函数、哪张表、哪个字段？
2. **前提是什么**：它假设的运行环境、调用者行为和输入数据在现实中真的存在吗？
3. **证据是什么**：是否有具体的报错日志、堆栈跟踪或明确违背的 SPEC 文本？

## 二、痛点与方案解耦法则 (Separate "Why" from "How")

审查者有时嗅觉敏锐，察觉到了真正的隐患（Why），但由于缺乏对全局架构的克制，给出了具有破坏性或膨胀化的方案（How）。

### 1. 解耦矩阵

```
                ┌────────────────────────────────────────────────────────┐
                │                  审查者指出的问题 (Why)                 │
                └───────────────────────────┬────────────────────────────┘
                                            │
                     ┌──────────────────────┴──────────────────────┐
                     ▼                                             ▼
             【隐患真实存在】                               【隐患系凭空捏造】
                     │                                             │
      ┌──────────────┴──────────────┐                              ▼
      ▼                             ▼                     【彻底驳回 (Reject)】
【方案合理克制】              【方案过度/伪需求】              指出其前提在代码中不成立
      │                             │
      ▼                             ▼
【直接采纳】                  【方案驳回 + 最小解替代】
实施修改                      驳回庞大方案，保留其痛点，
                             提供 3~5 行轻量修复代码
```

### 2. 真实案例模式
- **现象**：审查者指出“用户可能会在离线模式下触发网络同步报错，因此必须重构一套离线优先的本地事件回放引擎”。
- **解耦处理**：
  - **Why（隐患）**：离线状态下调用同步 API 会抛未捕获异常（真实存在）。
  - **How（过度方案）**：写离线事件回放引擎（过度工程，超纲伪需求）。
  - **处置**：驳回重构引擎的建议；改为在同步入口处增加 `if (!isOnline) return;` 并弹出友好提示（3 行代码解决核心问题）。

## 三、四维真实性校验铁律 (4-D Validation Shield)

每一条建议必须同时通关以下四层检验：

### 1. 维度一：需求基准校验 (Scope Check)
- **基准物**：原 Issue 描述、PRD 范围、当前任务上下文。
- **红线**：
  - 属于当前任务未承诺的“增强特性”或“后续规划”？→ **标为超纲，移交人工**。
  - 假借优化之名，擅自修改已经确认的需求边界？→ **驳回**。

### 2. 维度二：代码事实与调用链路校验 (Code Reality Check)
- **基准物**：当前分支的真实代码、依赖关系、数据流向。
- **红线**：
  - 审查者声称“这里可能传入非法类型”，但上游通过 TypeScript 严格类型断言或 Zod Schema 已经百分之百过滤？→ **假阳性，驳回**。
  - 审查者声称“会引发并发冲突”，但在单进程/单线程主控下运行，根本不存在并发写？→ **假阳性，驳回**。

### 3. 维度三：项目既定契约校验 (Project Invariants Check)
- **基准物**：[AGENTS.md](../../AGENTS.md)、ADR 架构决策记录、团队工程规范。
- **本项目的硬性契约**（随时根据 AGENTS.md 扩展）：
  - **数据库契约**：应用尚未上线，数据库结构变更直接修改创世基线 `GENESIS_V1_SCHEMA`，**严禁**编写 `ALTER TABLE` 迁移脚本；本地为单一主库 `firefly-ai-folder.db`。
  - **语义库契约**：**禁止**业务代码引用 `semantic.raw.db`，必须使用加密包 `semantic.pack` 并由 Omni 独占托管。
  - **包管理与平台**：代码基于 Windows 平台；包管理器使用 `pnpm` / `pnpm dlx`（禁止 `npx`）；代码与注释必须使用中文。
  - **注释契约**：严禁随意删除已有注释，除非注释本身错误。

### 4. 维度四：攻防经济学与威胁模型真实性校验 (Threat Model & Attack Economics Check)
- **基准物**：资产真实经济价值、封闭性/不可流通性、现实攻击算力/法律成本、客户端可用性与误杀代价。
- **红线**：
  - **资产价值失配**：将几十元封闭、不可提现、不可转账的单机工具代币当做千万级加密货币冷热钱包来防御？→ **学术型过度工程，驳回**。
  - **荒谬假想敌**：假想黑客能在 $2^{256}$ 空间盲猜物理机器码，或者愿意冒被抓判刑风险用强实名微信绑定受害者账户盗取代币？（攻击收益远低于现实法律与算力成本）→ **假想敌伪威胁，驳回**。
  - **误杀与客诉爆炸**：提出的防御方案（本地秘密 HMAC 签名、公钥信任根分发、管理员二次验证、支付 Ticket 二次确认等复杂 PKI）在单机多变环境下极易因重装、硬件变动导致密钥失配，引发正常用户大面积误杀与恶性客诉？→ **严重违背 KISS 原则，一票否决，坚决驳回**。
  - **转化漏斗劣化与过度状态机**：为了 0.0001% 的极端小概率手误（如扫码付错机器），在核心转化链路（如支付到账）强加阻断弹窗质问用户二次确认，或凭空设计 pending_confirm 待确认状态与多套 RPC？（劣化 99.9999% 付费用户的即时满足感，极端手误原本人工客服几秒钟即可后台换绑）→ **严重劣化核心商业转化漏斗，过度工程，坚决驳回**。

## 四、改动爆炸半径与 ROI 评估 (Blast Radius & ROI)

当一条建议属于“可用可不用”的技术整洁度改进时，根据爆炸半径评估是否采纳：

| 评估指标 | 低风险 (可直接采纳) | 高风险 / 过度工程 (原则上驳回) |
| :--- | :--- | :--- |
| **影响文件数** | 1 ~ 2 个局部文件 | 跨越核心接口、涉及十几个模块 |
| **对外契约兼容性** | 保持签名不变，内部纯函数优化 | 破坏既有 IPC 通道、修改公开 API 签名 |
| **数据迁移成本** | 零数据改动 | 需要清除用户本地老数据或做全量重扫 |
| **发生概率 vs 成本** | 高频必现，修复成本极低 | 极端边界（概率 < 0.1%），却要求引入 500 行中间层 |

## 五、异议反驳与建设性话术规范

提出异议时，严禁情绪化对攻，必须做到**“有据可查、语气平静、事实说话、给出出路”**。

### 1. 规范句式结构
1. **肯定动机（若有）**：“审查意见对 [某潜在边界] 的关注是有启发性的。”
2. **指出断层与代码事实**：“然而在当前代码实现中，根据 `[文件路径:行号]`，实际数据流为 `xxx`，因此假想的 `yyy` 场景在物理上无法发生 / 当前任务范围为 `zzz`，该意见超出了既定范围。”
3. **出具建设性方案**：“若希望彻底消除该顾虑，建议不要引入 [庞大机制]，仅需在 `[具体位置]` 添加 [最小补丁]，既能防范风险，又符合 KISS 原则与当前系统契约。”

## 六、必须停下请求人工裁决的判定标准

当遇到以下情形之一时，Agent **不得擅自裁决**，必须整理成明确的单选/多选题提请人工决策：
1. **超出当前任务范围，但确有长远商业/架构价值**（需人工决定是立刻建新需求池，还是彻底忽略）。
2. **涉及主观交互或产品策略变更**（例如提示文案倾向、破坏性弹窗阻断与否）。
3. **架构方案存在平分秋色的两难取舍**（例如内存占用 vs 响应速度不可兼得）。
4. **现有代码与历史文档存在冲突**，无法判定哪方为权威事实。
