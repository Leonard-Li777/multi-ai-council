# Review 去伪存真实战案例库 (EXAMPLES)

本文件列举了 4 个典型场景的审视对抗案例，展示如何将大词剥离、事实核验与建设性替代落到实处。

---

## 案例一：大词压人 + 凭空捏造配额伪需求（加戏造需求反驳范本）

### 用户粘贴的 Review 意见
> “立足于第一性原理（First Principles Thinking）、KISS 原则（简洁至上）以及本项目的真实商业与代码事实，经过深度排查，上一轮 Review 意见中除了前面提到的‘按天滚动免费额度’外，还存在以下 4 个极其不合理、脱离实际业务甚至具有破坏性的结论：
> 1. 没有考虑到并发高频请求下的商业配额击穿风险，必须在此处接入‘按天滚动计费限流中间件’；
> 2. 现有的标签打标缺少用户配额审计日志，属于破坏商业闭环的重大缺陷，必须新增 quota_audit_logs 数据库表。”

### `review-vet` 审视与输出示范

```markdown
### 🛡️ Review 结论去伪存真审视报告

#### 一、总览判定
- 建议总数：2 条
- ❌ 坚决驳回（凭空臆想 / 伪需求）：2 条

#### 二、逐条剖析与去伪存真

1. 【意见 #1：接入按天滚动计费限流中间件】
   - 判定：❌ **驳回（凭空捏造伪需求 / 越权加戏）**
   - 剥离大词：剥离“第一性原理、KISS、商业与代码事实、破坏性”等修辞定性，其实质主张是在当前标签补丁中硬塞一套商业计费与限流模型。
   - 事实依据：
     1. **需求基准**：当前 PR/任务为“本地标签元数据打补丁”，整个产品目前定位为桌面单机端运行（见 `AGENTS.md`），根本不存在所谓的“按天滚动商业配额”既定需求。
     2. **代码事实**：当前接口为本地主进程 IPC 调用（`ipcRenderer.invoke`），不存在多租户并发击穿云端服务的物理场景。
   - 痛点提纯与建设性方案：若审查者初衷是担心用户极端高频点击导致前端卡顿，其合理出路是**在前端触发按钮增加防抖（debounce 300ms）**，而不是凭空发明一套商业计费限流系统。

2. 【意见 #2：新增 quota_audit_logs 数据库表】
   - 判定：❌ **驳回（伪需求连锁反应）**
   - 事实依据：作为意见 #1 的衍生附属物，基于不存在的假想需求而膨胀出的数据表，严重增加本地数据库冗余，且违背 KISS 原则。
```

## 案例二：违反项目既定硬性契约（契约冲突一票否决范本）

### 用户粘贴的 Review 意见
> “检测到数据库字段 `tag_aliases` 发生了结构变动。根据生产环境数据库变更规范，严禁直接在建表语句中新增字段！必须在 `src/electron/runtime-services/database/migrations/` 下新增递增的 migration 脚本（例如 `0002_add_tag_aliases.sql`），并实现 `up` 和 `down` 双向迁移逻辑，否则上线后会导致用户数据丢失。”

### `review-vet` 审视与输出示范

```markdown
### 🛡️ Review 结论去伪存真审视报告

#### 一、总览判定
- 建议总数：1 条
- ❌ 坚决驳回（严重违反本项目既定架构契约）：1 条

#### 二、逐条剖析与去伪存真

1. 【意见 #1：禁止直接改建表语句，必须编写 ALTER TABLE 迁移脚本】
   - 判定：❌ **驳回（违反项目明确规则）**
   - 契约依据：
     1. 根据根目录 `AGENTS.md` 中【版本与兼容性】章节的绝对权威规定：
        > *“应用尚未上线，因此数据库 schema 变更无需考虑迁移兼容：直接修改创世基线 `GENESIS_V1_SCHEMA` 即可，不必编写 `ALTER TABLE` 迁移，`migrations` 数组保持仅 `version: 1`（见 ADR-0045）。”*
     2. 审查意见盲目套用常规线上 Web 项目的运维经验，完全脱离了当前仓库明确记载的工程契约。
   - 正确执行动作：严格按照项目规范，将改动合并入 `GENESIS_V1_SCHEMA` 基线，不引入多余的 migration 文件。
```

## 案例三：真实隐患但方案过度（Why 为真，How 走偏的提纯范本）

### 用户粘贴的 Review 意见
> “在处理大文件分析时，`multimodal-model-service.ts` 的模型调用如果遇到大尺寸损坏图片，底层推理进程可能长时间无响应导致整个桌面卡死。建议引入分布式的 BullMQ / Redis 任务队列，配合独立的 Watchdog 巡检守护进程来管理推理任务生命周期。”

### `review-vet` 审视与输出示范

```markdown
### 🛡️ Review 结论去伪存真审视报告

#### 一、总览判定
- 建议总数：1 条
- 🔄 方案驳回，痛点提纯并提供最小替代方案：1 条

#### 二、逐条剖析与去伪存真

1. 【意见 #1：引入分布式任务队列与独立的 Watchdog 进程】
   - 判定：🔄 **驳回原方案（过度工程），采纳其揭示的超时隐患（真问题）**
   - 剥离与解耦：
     - **Why（真实隐患）**：确实成立！查验 `multimodal-model-service.ts:88`，当前 `fetch` 调用确实未设置 `AbortSignal.timeout`，若模型服务挂起，Promise 会一直处于 pending 状态。
     - **How（过度方案）**：在单机 Electron 客户端中引入 Redis/BullMQ 等分布式队列纯属过度工程，极大增加了运行环境依赖与安装包体积。
   - **建设性最小可行方案（ROI 最高解）**：
     保留现有轻量架构，仅需在请求中传入 15 秒超时控制器，即可彻底消除挂死风险（仅需 3 行代码改动）：
     ```ts
     // 推荐替代：在 multimodal-model-service.ts:88 传入超时信号
     const response = await fetch(url, {
       ...options,
       signal: AbortSignal.timeout(15000), // 15秒无响应自动熔断并抛出友好错误
     });
     ```
```

## 案例四：超出当前任务范围但有价值（提请人工裁决范本）

### 用户粘贴的 Review 意见
> “本次修复了视频元数据提取中的时长与编码解析。建议顺便增加对 MKV 和 FLV 容器格式中内嵌多音轨与多字幕轨的深度探测，以便在虚拟目录中支持‘字幕语言’维度筛选。”

### `review-vet` 审视与输出示范

```markdown
### 🛡️ Review 结论去伪存真审视报告

#### 一、总览判定
- 建议总数：1 条
- ⚠️ 超出当前需求范围（提请人工裁决）：1 条

#### 二、逐条剖析与去伪存真

1. 【意见 #1：增加多音轨与字幕轨深度探测并扩展虚拟目录新维度】
   - 判定：⚠️ **超出当前范围（Scope Creep）**
   - 事实分析：
     - 当前 Issue #128 的目标仅为“修复 MP4/MOV 基础时长提取精度”，并不涵盖多字幕容器探测；
     - 增加字幕维度还需要同步修改前端维度树组件与数据库关联表，改动爆炸半径过大（预估涉及 6 个以上模块）。
     - 但该功能在产品长远规划中具有一定体验价值。

#### 三、请人工决断
关于意见 #1，请选择后续处理方式：
- [ ] **选项 A（推荐）**：当前 PR 暂不实施，由我将其整理并提交为独立的 Feature Request Issue，后续迭代统一排期。
- [ ] **选项 B**：当前直接忽略，暂不考虑。
- [ ] **选项 C**：追加进当前任务（需承担当前分支交付延期的风险）。

## 案例五：学术型假想敌防御与金融级妄想症（代币与机器码真实案例反驳范本）

### 用户粘贴的 Review 意见
> “当前萤火代币扣减和设备绑定存在巨大安全漏洞！攻击者可以伪造其他受害用户的 64 位机器码，在支付时直接消耗受害者的代币！系统必须引入本地秘密 HMAC 签名、公钥信任根分发体系，并在每次支付时要求企业管理员邮箱二次验证与未绑设备 Ticket 二次确认，确保单机代币支付的绝对零信任安全！”

### `review-vet` 审视与输出示范

```markdown
### 🛡️ Review 结论去伪存真审视报告

#### 一、总览判定
- 建议总数：1 条
- ❌ 坚决驳回（学术型假想敌过度工程 / 严重违背 KISS 原则）：1 条

#### 二、逐条剖析与去伪存真

1. 【意见 #1：引入本地 HMAC 签名、公钥信任根分发与支付二次 Ticket 验证】
   - 判定：❌ **驳回（学术型过度工程 / 荒谬假想敌防御）**
   - 剥离大词：剥离“巨大安全漏洞、绝对零信任、伪造攻击”等恐吓性修辞，其实质主张是在单机工具软件中引入一套复杂的企业级 PKI 与双因素支付验证体系。
   - 攻防经济学与事实依据：
     1. **资产价值与流通性严重失配**：本软件为售价几十元的单机桌面端工具，代币（萤火）不可转账、不可提现、封闭在单机软件内用于功能消费，根本不是数千万元资金的加密货币冷热钱包或银行金库！
     2. **算力空间事实**：受害者物理机器码是 64 位 SHA256 哈希，穷举空间为 $2^{256}$，黑客在数学上盲猜碰撞概率恒等于 0。
     3. **现实法律与强实名制威慑**：在中国境内，设备绑定与支付依赖强实名体系（绑定身份证与银行卡的微信支付）。假想一个黑客冒着被刑事追责的巨大风险，把自己的强实名微信号焊死在受害账户上，只为了盗取不可变现的几十块工具代币，在现实攻防经济学上是极度荒谬的虚构假想敌！
     4. **可用性致命与误杀客诉风险**：引入“本地秘密 HMAC 签名、公钥信任根分发、管理员邮箱二次验证、未绑设备支付二次 Ticket 确认”等庞大脆弱的 PKI 体系，不仅研发维护成本暴增数倍，更会在真实用户重装系统、硬件微调、离线使用时频繁发生密钥失配，引发大面积误杀正常付费用户与恶性客诉，严重违背 KISS 简洁至上 原则。
   - 痛点提纯与建设性方案：
     云端只需在微信支付回调中校验微信 OpenID 与机器码绑定关系，单次支付依赖现有微信支付安全凭据即可；**坚决不向本地客户端引入任何脆弱的 PKI 与多因素验证体系**。
```

## 案例六：极端偶发手误防御与核心转化漏斗破坏（支付与绑定二次确认反驳范本）

### 用户粘贴的 Review 意见
> “审查发现，用户在小程序扫码支付时，可能存在手误扫错二维码或绑定错误物理机的情况（F-36 ~ F-39）！为了防止错误绑定与代币误充，系统必须引入 `pending_confirm` 待确认状态、确认绑定 RPC、拒绝解绑 RPC，并在电脑端弹出阻断式二次确认弹窗质问用户：‘这是不是您的设备？请确认/拒绝’。确认后才允许发放权益。”

### `review-vet` 审视与输出示范

```markdown
### 🛡️ Review 结论去伪存真审视报告

#### 一、总览判定
- 建议总数：1 条
- ❌ 坚决驳回（严重劣化核心商业转化漏斗 / 制造无效状态机与代码）：1 条

#### 二、逐条剖析与去伪存真

1. 【意见 #1：增加 pending_confirm 待确认状态、二次确认弹窗与确认/解绑 RPC】
   - 判定：❌ **驳回（转化漏斗自毁 / 极端偶发过度工程）**
   - 剥离大词：剥离“防错充、防串号、数据一致性”等修辞，其实质是在用户付费后的核心到账链路强塞一道阻断弹窗与一套异步确认状态机。
   - 事实与商业依据：
     1. **真实场景根本不存在串号动机**：用户就是个人用户，坐在自己的个人电脑前，打开自己的手机微信扫码付款，充值目标百分之百是眼前这台物理机，串号概率低于十万分之一。
     2. **极度破坏核心商业转化漏斗**：用户用手机花了几十或数百元真金白银完成付款，预期的是回到电脑前屏幕上的代币与权益秒级到账、获得强烈的即时满足感。此时弹窗质问“这是不是你的账号？请点击确认”，体验极度怪异，严重破坏付费体验与用户信任度。
     3. **制造大量无效代码与脆弱状态机**：为了一个十万分之一的手误，凭空多出 2 个 RPC、2 个数据表状态枚举、4 种前端文案分支和一系列网络重试、超时撤销逻辑，严重违背 KISS 简洁至上 原则。
     4. **兜底手段倒挂**：十万分之一的罕见手误，属于典型的人工客服兜底场景。万一真有用户误操作，人工客服几秒钟在后台换绑即可解决，绝不能用系统复杂度与 99.9999% 正常用户的体验牺牲去换取所谓的代码自动化闭环！
   - 痛点提纯与建设性方案：
     支付回调成功后，云端原子完成机器码绑定与代币权益入账，客户端长轮询或推送秒级刷新余额，**绝不弹窗阻断质问**。
```
