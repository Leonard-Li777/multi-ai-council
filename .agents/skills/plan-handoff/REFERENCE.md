# 方案外部审查移交参考手册 (REFERENCE)

本手册详细规范了生成面向外部第三方（无本地仓库访问权）的方案审查提示词时的核心模块、XML 隔离协议、代码签名提取规则、防脑补纪律、升维方案探索协议与结构化对齐模板。

---

## 一、自包含设计的四大核心工程原则

### 1. 零外部依赖直书原则 (Zero-External-Dependency)
外部评审者（Web 端 Claude、ChatGPT、外部专家等）物理上无法访问本地工作区：
- **严禁使用本地相对路径**（如 `docs/specs/...`、`../../AGENTS.md`）；
- **外部文档标注规范**：注明文档全名与公开直达链接（如 GitHub Issue URL、RFC 链接）；
- **核心内容就地展开**：所有审查所必需的上下文、业务前因后果、ADR 决策与存量代码签名，**必须直接在提示词内部直书展开**。

### 2. XML 语义标签物理隔离 (XML Semantic Tagging)
为了避免方案内原有的 Markdown 语法、表格与反引号代码块（```）引起解析错乱，整个提示词内部的核心板块强制使用 XML 标签包裹：
- `<review_mandate>`：审查使命、防脑补铁律、升维探讨指引与防假想敌过度防御铁律
- `<business_context_and_threat_model>`：业务现实、资产价值与攻防经济学模型（防学术型过度工程）
- `<system_invariants>`：不可动摇的系统底线契约
- `<codebase_interface_snapshot>`：存量代码接口与类型快照
- `<inlined_references>`：关联的外部文档与核心 ADR 原文直书
- `<rejected_alternatives>`：已否决的备选方案与理由
- `<target_plan>`：带 `[PLAN-SEC-XX]` 锚点的方案全文
- `<focus_areas>`：开发者重点疑虑与主动挑刺清单
- `<output_template>`：结构化输出元数据模板（含升维方案插槽）

### 3. 首尾双锚定防衰退 (Sandwich Prompting)
外部 LLM 在处理超长上下文时存在“中间遗忘（Lost-in-the-Middle）”倾向。为此：
- **首部锚定**：在开头的 `<review_mandate>` 中宣布审查标尺、防加戏纪律、防脑补铁律与升维探讨通道；
- **尾部呼应**：在末尾 `<output_template>` 输出前设置唤醒检查单：
  > *“在给出最终结论前，请再次核验：你的建议是否违反了 `<system_invariants>` 的底线？是否落入了 `<rejected_alternatives>` 已否决的死胡同？”*

### 4. 智能裁剪直书与预算控制 (Smart Inlining)
- **待审查方案 (`<target_plan>`)**：100% 完整保留，不得删减任何逻辑；
- **参考文档与 ADR (`<inlined_references>`)**：仅提取与本方案产生直接契约关联的**决策条目、状态流转与约束定义**，剔除无关的历史叙旧与讨论背景，控制整体信噪比。

## 二、防脑补免责声明与质询协议 (Anti-Hallucination Protocol)

外部模型常存在“强行完形填空”和“基于脑补假设批判”的倾向。必须在 `<review_mandate>` 中强制注入以下约束：

> **【防脑补铁律】**：  
> 1. 本提示词已提供了评估该方案所需的全部必要上下文。如果某项推演必须依赖本文未提及的外部模块实现细节，**严禁自行脑补假设并基于该假设展开批判**；  
> 2. 遇到信息真空时，请直接归类为 `❓ 待确认上下文 (Missing Context Question)`，客观指出：“若系统现状为 X，则存在 Y 隐患；若现状为 Z，则该处合理”。

## 三、业务现实与攻防经济学评估协议 (Attack Economics & Anti-Phantom-Threat Protocol)

外部评审者极易陷入“脱离实际业务场景的学术型过度工程与假想敌防御”陷阱。为此，提示词必须通过 `<business_context_and_threat_model>` 强行锚定真实业务价值与攻防经济学边界：

### 1. 资产价值与防御成本对等原则 (Asset-Value Parity)
- **明确资产属性**：必须在提示词中交代资产的真实经济价值与流通性。例如：本项目为几十元售价的单机桌面端工具软件，内部代币不可转账、不可提现、封闭在单机客户端内部消耗；
- **严禁金融级妄想症**：严禁把几十块钱的工具软件代币，当做几千万资金的加密货币冷热钱包在防御；任何防御机制的开发成本、维护代价与心智负担，不得超过被保护资产本身的价值量级。

### 2. 攻击者画像与现实成本约束 (Real Attacker Economics & Legal Bounds)
- **拒绝假想无敌黑客**：严禁假想“攻击者拥有无限算力、不计成本，且愿意冒着严重法律风险自投罗网”；
- **必须核验现实物理与法律成本**：
  1. **算力空间事实**：物理机器码（如 64 位 SHA256）的可能空间为 $2^{256}$，盲猜碰撞概率在物理上恒等于 0；
  2. **强实名制威慑**：在中国境内，支付与登录依赖强实名体系（绑定身份证与银行卡的微信支付/手机号），攻击者若要盗号消费，必须将自己的强实名账号焊死在受害账户上，为盗取几十块不可变现代币承担刑事追责风险，在现实中是荒谬且不可能的假想敌；
- **假想敌判定即否决**：若推演出的攻击场景在现实中收益微薄但成本/风险极高，直接归类为 `❌ 假想敌伪威胁`，方案严禁为此加戏设计防御。

### 3. 误杀率与可用性一票否决权 (False Positive & Usability Veto)
- **单机环境的脆弱性**：本地私钥/HMAC 签名、公钥信任根分发、管理员邮箱二次验证、未绑设备支付二次 Ticket 确认等庞大脆弱的 PKI 体系，极易因用户重装系统、硬件微调、离线使用、网络波动发生密钥失配；
- **误杀与客诉代价为首要公理**：在工具软件中，**正常用户的可用性与零客诉远重于微小假想风险的绝对防御**。一旦防御方案会引入密钥失配风险、频繁弹窗打扰正常用户或增加误杀可能，即属严重违背 KISS 原则，必须一票否决！

## 四、升维审视与替代方案探索协议 (Higher-Dimensional Paradigm & Alternatives Protocol)

外部模型在审查方案时，极易陷入“受限在既定路线内做局部的补丁式校对”这一陷阱，导致“在错误或低效的方向上精雕细琢”。为此，提示词必须显式赋予外部审查者**更高维度的破局授权**：

### 1. 破除局部最优陷阱 (Break Local Optima Trap)
- **拒绝单纯充当“校对员”**：审查者不仅要核验当前方案的具体步骤是否可行，更要后撤一步、站到全局系统架构与第一性原理高度审视：**这个方案解决问题的姿态是否过于别扭？是否在给错误的前提打复杂的补丁？**
- **鼓励“降维打击”与根本性化繁为简**：是否存在一种更高的抽象、更优的数据流范式或现有基础设施的优雅复用，能直接**从源头上消灭**本方案试图用大量状态机和缓存去防御的复杂性？

### 2. 升维方案准入标准
任何提出的升维替代方案必须满足：
1. **恪守系统硬契约**：严禁借升维之名引入分布式中间件等违反 `<system_invariants>` 的设计；
2. **复杂度实质下降**：新范式必须带来可观的复杂度下降、更少的并发竞态点或更长远的演进收益；
3. **结构化呈现**：通过 `<output_template>` 中的专用对比插槽输出，以便本地通过 `/review-vet` 快速对齐。

---

## 五、存量代码签名提取规范 (Codebase Interface Snapshot)

在 `<codebase_interface_snapshot>` 中，提取与本方案直接交互的核心代码骨架：
- **只提取类型签名**：TypeScript `interface` / `type`、Rust `struct` / `enum`、SQL DDL 建表语句；
- **坚决剔除实现细节**：函数体用 `...` 省略，只保留方法名、入参和返回类型；
- **价值**：以极小的 Token 开销把外部审查者牢牢锁定在真实的数据结构上，杜绝凭空发明不存在的字段或方法。

## 六、结构化对齐协议：无缝对接 `/review-vet`

为了使外部审查者返回的文本能够毫无阻碍地被本地 [/review-vet](../review-vet/SKILL.md) 自动化去伪存真，必须在生成时建立双向元数据对齐：

### 1. 方案段落打标 (Input Anchors)
在 `<target_plan>` 内部，为主 Agent 方案的核心章节打上显式锚点编号：
- 架构总览：`[PLAN-SEC-01: 整体架构]`
- 核心改动：`[PLAN-SEC-02: 数据持久化与索引]`
- 异常兜底：`[PLAN-SEC-03: 离线与超时降级]`
- 任务切片：`[TASK-01: 创世基线补全]`、`[TASK-02: 内存倒排索引]`

### 2. 审查输出元数据模板 (Output Contract)
在 `<output_template>` 中，强制要求外部审查者按照统一元数据结构反馈：

```markdown
### [ISS-01] 简短问题标题
- **关联方案锚点**：[如 PLAN-SEC-02 或 TASK-01]
- **严重级别**：🔴 阻断缺陷 (Blocker) | 🟡 边界隐患 (Edge Case) | 🟢 超纲高性价比建议 (Out-of-Scope Gem) | ❓ 待确认上下文
- **推演路径与触发条件**：[在何种具体并发/异常/脏数据下会产生破坏]
- **修改建议**：[具体怎么修改方案]
```

### 3. 升维替代方案专用插槽 (Alternative Paradigm Contract)
若审查者发现了根本性更优范式，在末尾统一填入结构化对比：
```markdown
### [ALT-PARADIGM] 升维更优方案探讨
- **核心思路与升维视角**：[简述跳出当前方案思路的新方案核心]
- **方案对比矩阵**：
  | 维度 | 当前方案 | 升维更优方案 |
  | :--- | :--- | :--- |
  | 复杂度与代码量 | ... | ... |
  | 架构优雅度与健壮性 | ... | ... |
  | 实施风险与改造代价 | ... | ... |
- **推荐落地路径**：[直接重构替换 / 还是渐进式演进]
```

## 七、环境自适应模式 (Modes)

- **AI 红队模式（默认）**：
  采用严谨的 XML 包装、反脑补铁律、升维探讨指引与结构化 `[ISS-XX]` / `[ALT-PARADIGM]` 输出格式，专为投喂 Web 端 Claude、ChatGPT、o1 等大模型设计。
- **人类专家 RFC 模式（可选）**：
  当用户明确要求“打包发给人类架构师/外部同事”时，去除 Prompt 角色扮演腔调，将 XML 标签转换为标准的 Markdown 标题（`<target_plan>` 转换为 `# RFC 方案征求意见稿`），语言更贴合人类团队协作。

## 八、自包含提示词装配模版 (Template)

每次调用 `/plan-handoff` 时，替换占位符生成完整的提示词：

````markdown
# 架构与方案审查委托：[方案名称]

<review_mandate>
你好！请作为资深系统架构师与严苛的红队审查员，对以下方案进行深度、严谨且建设性的专业审查。

【审查原则与铁律】：
1. **事实为本**：所有指出的技术缺陷与物理死穴，必须基于方案所陈述的调用链路与存量代码签名，严禁脱离实际凭空挑刺；
2. **【防脑补铁律】**：如果某个判断依赖于本文未提供的外部上下文，**严禁自行脑补假设并展开批判**。请直接归类为 `❓ 待确认上下文`；
3. **欢迎高性价比超纲建议**：如果发现了超出本次任务目标但具有极高架构演进价值或极小成本撬动大收益的好点子，请显式打上 `🟢 超纲高性价比建议` 标签并说明 ROI！
4. **【升维审视与替代方案探讨】**：不要只做当前方案细节的“代码校对员”！请跳出当前方案设定的局部思维框框，从更高架构维度与第一性原理审视：当前方案是否陷入了局部最优？是否存在根本性简化系统、从源头消灭问题、或架构更优雅的“降维打击”更优解？如果有，极度欢迎在评审末尾专门输出《升维更优方案探讨 (Alternative Paradigm Proposal)》，阐明为什么新方案更好，并给出对比与迁移思路；
5. **【防假想敌过度防御与攻防经济学铁律】**：严禁脱离实际业务场景做学术型过度工程与假想敌防御！必须严格以资产实际价值（如几十元不可转账、不可提现、封闭在单机软件内部的工具代币 vs 数千万加密货币冷钱包）和真实攻防经济学为标尺。严禁假想攻击者为了盗取微不足道且不可变现的资产，愿意付出极高现实法律成本（如强实名微信/银行卡绑定被追责）或天文级算力成本（如盲猜 2^256 物理机器码）；严禁为了防御此类假想敌而建议引入本地秘密 HMAC 签名、公钥信任根分发、管理员邮箱二次验证、未绑设备支付二次确认等庞大脆弱的 PKI 体系！此类过度工程不仅开发维护成本飙升数倍，更会在真实用户重装、硬件变动、网络抖动时因密钥失配导致严重误杀和恶性客诉，严重违背 KISS 简洁至上 原则！
</review_mandate>

<business_context_and_threat_model>
【业务现实、资产价值与攻防经济学约束】：
- **产品与资产属性**：[如：单机桌面端工具软件，内部代币为不可转账、不可提现、封闭在单机客户端内部消耗的低价值积分，绝非开放金融资产]
- **现实攻击成本与法律约束**：[如：国内用户通过微信/手机号强实名认证，攻击者盗号必然暴露强实名身份；机器码为 64 位 SHA256，盲猜空间 2^256 概率物理为 0]
- **可用性与误杀红线**：严禁采用会导致真实用户因硬件变动、系统重装而发生密钥失配、操作受阻的脆弱防御机制。任何导致误杀客诉的过度设计均属不可接受。
</business_context_and_threat_model>

<system_invariants>
【不可动摇的系统底线与既定契约（任何违背本节的建议均属无效）】：
- [系统契约 1，如：项目未正式上线，数据库结构变更直接修改创世基线 GENESIS_V1_SCHEMA，严禁设计 ALTER TABLE 迁移脚本]
- [系统契约 2，如：业务代码严禁直接寻址 semantic.raw.db，必须走 Omni 托管解密的 semantic.pack]
- [系统契约 3，如：单机桌面端运行环境，严格遵循 KISS 原则，拒绝无谓引入分布式中间件]
</system_invariants>

<codebase_interface_snapshot>
【与本方案直接交互的存量核心代码签名快照】：
```ts
[此处仅粘贴核心 Interface/Type/DDL 签名，不贴函数实现]
```
</codebase_interface_snapshot>

<inlined_references>
【参考文档与核心决策原文直书】：
- **关联 Issue**：[Issue 标题及公开 URL]
- **核心 ADR 决策原文直书**：
  > [此处内联摘录关键 ADR 决策条款与规则]
</inlined_references>

<rejected_alternatives>
【已被讨论并正式否决的备选方案（请勿再重复提议以下路线）】：
- 否决方案 1：[方案名称] ➔ 否决原因：[因何种成本/风险舍弃]
</rejected_alternatives>

<target_plan>
【待审查方案全文直书】：

### [PLAN-SEC-01: 方案背景与目标]
- 交付目标 (In-Scope)：...
- 明确非目标 (Explicit Non-Goals)：...

### [PLAN-SEC-02: 架构与模块设计]
...

### [PLAN-SEC-03: 悲观路径与异常兜底]
...

### [PLAN-SEC-04: 垂直任务切片与量化验收标准]
- [TASK-01]: ...
  - AC 1: [ ] ...
</target_plan>

<focus_areas>
【开发者核心疑虑与重点挑刺清单（请重点审查）】：
1. [疑虑点 1：如并发竞态、异常回滚是否完备]
2. [疑虑点 2：如内存消耗估算是否合理]
</focus_areas>

<output_template>
【首尾双锚定唤醒检查单】：
在输出结论前，请再次核验：你的意见是否违反了 `<system_invariants>` 的底线？是否在提议 `<rejected_alternatives>` 中已被否决的方案？

【请严格按以下结构输出评审结论】：
### [ISS-01] 简短问题标题
- **关联方案锚点**：[填写对应的 PLAN-SEC-XX 或 TASK-XX]
- **严重级别**：🔴 阻断缺陷 (Blocker) | 🟡 边界隐患 (Edge Case) | 🟢 超纲高性价比建议 (Out-of-Scope Gem) | ❓ 待确认上下文
- **推演路径与触发条件**：[在何种并发/异常/脏数据下会产生破坏]
- **修改建议**：[具体怎么修改方案]

若从更高架构维度审视，存在比当前方案根本性更优的解法（如从根源消灭问题、复杂度大幅降低、更优雅的范式跃迁）：
- **核心思路与升维视角**：[简述跳出当前方案思路的新方案核心]
- **方案对比矩阵**：
  | 维度 | 当前方案 | 升维更优方案 |
  | :--- | :--- | :--- |
  | 复杂度与代码量 | ... | ... |
  | 架构优雅度与可扩展性 | ... | ... |
  | 实施风险与改造代价 | ... | ... |
- **推荐落地路径**：[直接重构替换 / 还是渐进式演进]
</output_template>
````
