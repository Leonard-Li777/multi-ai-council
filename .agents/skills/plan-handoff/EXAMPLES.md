# 方案外部审查移交实战案例库 (EXAMPLES)

本文件完整还原了一个基于 `plan-handoff` 生成的、面向外部无仓库访问权限评审者的自包含提示词成品，以及外部返回的结构化高信噪比反馈示例（包含细节缺陷排查与升维更优方案探讨）。

---

## 真实演练场景

开发者与 AI 完成了“智能标签多语言别名实时检索与持久化治理”的初版设计方案。现在需要将这份方案拿给**网页端 Claude 3.5 Sonnet / o1** 进行深度外部审查。由于外部模型无法访问本地仓库，调用 `/plan-handoff` 生成一份自包含的一键复制提示词。

---

### 二、外部审查者（如 Claude/o1）返回的结构化反馈

```markdown
### 评审意见回复

### [ISS-01] 别名写入时序存在微小窗口的内存幽灵读隐患
- **关联方案锚点**：[PLAN-SEC-02]
- **严重级别**：🟡 边界隐患 (Edge Case)
- **推演路径与触发条件**：方案写道“先写 SQLite，事务提交成功后再增量更新内存 Map”。在 SQLite 事务刚提交但内存 Map 尚未完成增量更新的瞬间（微秒级），并发读请求依然会命中老内存，产生短暂的展示与磁盘不一致。
- **修改建议**：在增量更新期间加读写锁保护，或采纳文末的升维方案根本性消灭该问题。

### [ISS-02] 增加拼音首字母匹配（Pinyin Acronym）支持
- **关联方案锚点**：[PLAN-SEC-01]
- **严重级别**：🟢 超纲高性价比建议 (Out-of-Scope Gem)
- **推演路径与触发条件**：虽然超出原 In-Scope，但中文桌面用户对输入拼音首字母（如 `bgr` 匹配“办公日记”）有极其强烈的本能习惯；且在存量代码签名中已存在 `raw_name`，内存加载时只需多计算并存储一个 8 字节的简拼字符串，零磁盘额外开销，收益极大。
- **修改建议**：在 `TagMatcher` 内存索引结构中扩展支持 `pinyin_acronym` 索引。

---

## 🌌 【升维更优方案探讨 (Alternative Paradigm Proposal)】

### [ALT-PARADIGM-01] 采用不可变快照原子替换 (Copy-On-Write Snapshot) 替代增量读写锁模型
- **核心思路与升维视角**：
  跳出当前方案中“在单机内存中维护可变 Map、通过 Mutex 加锁防并发竞态与脏读”的传统多线程锁思路。
  单机桌面环境下，标签别名总数通常仅几千条（全量内存 < 2MB）。当发生新增/修改时，直接在后台生成全新的不可变只读索引对象（Immutable Snapshot），随后在 JavaScript 单线程主控下执行一次**引用赋值（Atomic Pointer Swap）**！
- **方案对比矩阵**：
  | 维度 | 当前方案 (可变 Map + Mutex 增量锁) | 升维更优方案 (不可变快照原子替换) |
  | :--- | :--- | :--- |
  | **并发复杂度** | 需要 Mutex、读写锁、考虑回滚脏数据 | **完全零锁 (Zero-Lock)**，读操作永远命中冻结快照 |
  | **代码量与缺陷面**| 约 150 行并发同步与锁兜底逻辑 | **仅需 40 行纯函数**，无任何竞态或幽灵读可能 |
  | **内存与性能** | 内存极小，但增量写入易碎片化 | 仅在写入瞬间产生 2MB 短暂垃圾，GC 无感；匹配延迟 < 0.2ms |
  | **系统契约匹配度**| 合规 | 完全合规且极端践行 KISS 原则 |
- **推荐落地路径**：
  强烈建议**直接重构替换原方案的 PLAN-SEC-02/03**。由于尚未编写业务代码，在方案阶段直接转为不可变快照模式成本为零，却能彻底消除所有的并发死锁与幽灵读隐患。
```

### 三、下游闭环：拿回反馈后如何处理？

用户只需将上述外部返回的文本复制回本地会话，直接输入：
> **/review-vet** 处理这份来自外部 Claude 的评审反馈

本地 Agent 将自动以代码事实为准绳去伪存真：
1. 精准采纳 `[ISS-02]` 的超纲高性价比简拼索引；
2. 敏锐识别 `[ALT-PARADIGM-01]` 升维方案的极高价值（以函数式不可变快照消灭了 `[ISS-01]` 的锁缺陷，且代码量骤降 70%），主 Agent 可直接在 Spec 中将方案升级为原子快照架构！
