# Document Architect 详细参考规范与拓扑治理手册 (REFERENCE)

本文档是 `doc-architect` 技能的深层参考手册，定义了 4 环同心圆骨架、拓扑连接双铁律、文档生长机制、防腐废弃生命周期及标准模板库。

---

## 1. 4 环同心圆知识骨架与准入矩阵 (Concentric Ring Matrix)

系统技术文档划分为 4 个同心环级。层级越靠近内环，要求越精炼、稳定性越高；越靠近外环，内容越丰富详尽，迭代速度越快。

```
              ┌─────────────────────────────────────────┐
              │          第 4 环 (L4) 语境与历史           │
              │   (Retro 复盘 / Archive 归档 / Issue)   │
              │   ┌─────────────────────────────────┐   │
              │   │     第 3 环 (L3) 深度技术规格     │   │
              │   │   (Approved Specs / PRD / ADR)  │   │
              │   │   ┌─────────────────────────┐   │   │
              │   │   │  第 2 环 (L2) 领域规范与枢纽 │   │   │
              │   │   │ (Standards / Arch Hubs) │   │   │
              │   │   │   ┌─────────────────┐   │   │   │
              │   │   │   │ 第 1 环 (L1) 内核│   │   │   │
              │   │   │   │   (AGENTS.md)   │   │   │   │
              │   │   │   └─────────────────┘   │   │   │
              │   │   └─────────────────────────┘   │   │
              │   └─────────────────────────────────┘   │
              └─────────────────────────────────────────┘
```

| 环级 | 名称与定位 | 物理路径落点 | 职能范围 | 内容规模配额 | 异环相邻连接规则 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **L1** | **系统内核总枢 (Kernel)** | `AGENTS.md` (或 `CLAUDE.md`) | 全系统不可动摇底层红线、核心行为准则、L2 专项路由表 | $\le 120$ 行 (~10KB)<br>Prompt 常驻 | **仅允许连接 L2**<br>严禁跨级直连 L3/L4 |
| **L2** | **领域规范与枢纽 (Standards & Hubs)** | `docs/developer/standards/`<br>`docs/developer/infra/`<br>`docs/developer/architecture/`<br>`docs/developer/references/`<br>`docs/features/*/`<br>`docs/agents/` | 核心开发范式、全局架构总览、环境与单例字典、Agent 协同规范。作为承上启下枢纽，向下索引该领域的深度规格 | 建议 $\le 300$ 行<br>单次按需加载 | 向上连接 L1；<br>向下连接 L3；<br>同环可网状互联；<br>严禁直连 L4 |
| **L3** | **深度技术规格 (Deep Specs & PRDs)** | `docs/specs/`<br>`docs/prd/`<br>`docs/adr/` | 权威审定（Approved）的纵深技术方案、数据模型、PRD、架构决策 | 无严格行数上限<br>强制前 60 行带 TOC | 向上连接所属 L2；<br>向下连接 L4 历史；<br>同环鼓励多维网状互联；<br>严禁跨级连接 L1 |
| **L4** | **语境与历史沉淀 (Context & History)** | `docs/archive/`<br>`docs/research/`<br>`docs/issues/`<br>`docs/retro/` | 任务开发复盘 (Retro)、探索性调研报告、历史任务工单、已归档规范 | 自由格式<br>按需深度索骥 | 仅向上连接其支撑的 L3/L2；<br>严禁反向向 L1 渗透；<br>同环可多维关联 |

## 2. 知识拓扑连接双铁律 (Linking Invariants)

为了兼顾「网状知识多维串联」与「环形骨架层级防腐」，系统严格执行以下拓扑连接双铁律：

### 律一：同环自由网状互联 (Intra-ring Mesh Freedom)
- **同环无边界**：同处于第 $N$ 环的任意文档之间，允许且鼓励按业务语意多维度横向交叉互联。
- **价值**：例如在 L2 中，`testing-guide.md` 可以引用 `DEVELOPMENT.md`；在 L3 中，`tag-admissibility-filter-spec.md` 与 `content-rating-and-erotic-breakdown-ontology-refactor-spec.md` 相互引用。这种横向关联编织了立体的知识网络，消除了单向孤岛。

### 律二：异环严格单级相邻 (Inter-ring Strict Adjacency)
- **相邻级跳转**：跨环引用严格限制在相邻一级：
  $$\Delta \text{Ring} = | \text{Ring}_{\text{source}} - \text{Ring}_{\text{target}} | \le 1$$
- **反例与禁令**：
  - ❌ **严禁 L1 直连 L3/L4**：严禁在 `AGENTS.md` 中直接罗列数十篇具体 Spec 或归档任务（会导致 L1 暴涨数千行并快速腐化失效）；
  - ❌ **严禁 L2 跳级直连 L4**：L2 作为规范 Hub，应引导 Agent 查阅当前有效的 L3 规格，具体实施踩坑历史由 L3 在附录承接；
  - ❌ **严禁 L4 逆向直指 L1**：历史复盘与 Issue 严禁将自己直接挂载到根目录 `AGENTS.md`。

## 3. 会话级知识回流与提炼五维审查标准 (Five-Dimensional Session Review)

当开发任务、特性重构或会话收口时，文档架构专家（Agent）必须对照以下五维审查雷达进行全面排查，确保知识资产闭环：

### 维度 1：偏差修订排查与原文档就地纠偏 (Misunderstandings & Source Doc Correction)
- **判定标准**：会话中用户是否提出了反驳、纠正、概念澄清或技术方向纠偏？
- **处置原则与溯源三步法**：
  1. **溯源归因 (Root Cause Attribution)**：排查理解偏差产生的原因，深入核实是否是因为**既有原文档（L2 领域规范、L3 深度规格、架构说明等）自身存在陈述错误、定义过时、缺少边界条件或表述模糊**？
  2. **原文档就地纠偏 (Source In-place Fix)**：若偏差源于原文档缺陷，**严禁仅在口头回复或复盘日志中记录，必须立即返回该原文档对应章节进行就地勘误、澄清歧义并补充精准定义**，从源头消灭未来 Agent 或开发者再次误解的可能；
  3. **新增事实沉淀 (Knowledge Retention)**：将修正后的真实技术事实、反直觉陷阱或平台兼容性结论，沉淀至对应 L2 避坑指南（如 `DEVELOPMENT.md`）或 L3 深度规格中。

### 维度 2：领域模型提炼与 domain-modeling 联动 (Domain Modeling Trigger)
- **判定标准**：本轮任务是否涌现了新的核心实体、术语、受控概念枚举、状态机或概念边界？
- **处置原则**：若存在新术语或术语含义演变，**主动触发 `/domain-modeling` skill**，依照 `CONTEXT-FORMAT.md` 标准更新 `CONTEXT.md` 术语表；对于不可逆的重大架构抉择，依规提炼记录至 `docs/adr/`。

### 维度 3：相关文档联动与补充 (Related Docs Expansion)
- **判定标准**：改动是否波及其他关联模块？是否存在未同步更新的数据模型字典、服务字典或工作流文档？
- **处置原则**：检查 `public-services-catalog.md`、`v4-end-to-end-architecture.md` 等枢纽文档，补充缺漏的契约与说明，该创建的新文档立即创建，消灭断头知识。

### 维度 4：重要度升降级治理 (Promote & Demote Governance)
- **重要内容提升 (Promote)**：
  - 具有全系统不可动摇约束力的新底层红线 ➔ 提炼 1-2 行高密度原则原地提升至 L1 `AGENTS.md` §2（严守 $\le 120$ 行预算）；
  - 领域级架构范式与开发规范 ➔ 提升写入对应 L2 领域 Hub。
- **次要/过时内容降级 (Demote)**：
  - 被新方案取代的旧规范、历史废弃脚本或临时实现 ➔ 插入 `SUPERSEDED` 标头并移动至 L4 `docs/archive/`。

### 维度 5：复盘机制触发 (Retro Skill Trigger)
- **判定标准**：会话是否经历了复杂排障、多轮审查修复循环（`implement-loop`）、重大重构或全栈特性联调？
- **处置原则**：**主动建议或调用 `/retro` skill**，按照模板 D 将背景、踩坑经验与资产沉淀落盘至 L4 `docs/retro/YYYY-MM-DD-<topic>.md`。

## 4. 开发复盘 (Retro) 与知识沉淀标准化规程

当一个开发任务或会话结束，利用 `retro` 或需求沉淀技术资产时，必须遵循以下归位规程：

```
[开发任务收口 / Retro 复盘]
           │
           ▼
  1. 产出复盘原始记录 ────────── 归入 L4: docs/retro/YYYY-MM-DD-task-name.md
           │
           ▼ (提炼具有复用价值的技术知识)
  2. 是否产生新的权威技术方案?
     ├─► [是] ── 编写或更新 L3 Spec (docs/specs/xxx-spec.md)
     │            └─ 向上挂入对应领域的 L2 Hub (如 docs/developer/standards/xxx.md)
     │            └─ 向下在附录记录本次 L4 复盘链接
     └─► [否] ── 跳过
           │
           ▼ (提炼具有全局约束力的开发纪律)
  3. 是否形成新的全系统底层红线?
     ├─► [是] ── 提炼 1-2 行高密度原则原地写入 L1 AGENTS.md §2 (严守 120 行上限)
     └─► [否] ── 写入对应 L2 领域规范 (docs/developer/standards/xxx.md)
           │
           ▼
  4. 运行健康度门禁 ────────── node .agents/skills/doc-architect/scripts/check-doc-health.js
```

## 6. 防腐与语义废弃生命周期 (Anti-Rot Lifecycle)

### 6.1 废弃不硬删原则
技术演进过程中，旧规范被新方案取代时，**严禁物理静默删除旧文件**，否则会导致历史提交、Issue 以及其他未更新文档出现硬死链（404）。

### 6.2 废弃处理三部曲
1. **加注废弃标头**：在旧文档最顶部插入标准的「已废弃」警告块，指明继任文档；
2. **迁移归档**：将旧文档移动至 `docs/archive/` 对应子目录下（即降级为 L4）；
3. **父级切流**：更新其所属上一级 L2 Hub 或 L1 中的导航指针，将其替换为新文档地址。

## 7. 自动化目录导航 (TOC) 生成与查阅指南

### 7.1 TOC 架构定位与 Token 节约原理
系统所有重要技术文档（尤其 L2 领域规范、L3 深度规格）必须在开篇配备目录导航（前 60 行内）。
- **Agent 读取铁律**：Agent 查阅深度文档时，**严禁直接无限制全量读取**。必须先调用 `view_file` 读取前 60 行目录导航（TOC），获取对应小节名称或行号，再指定 `StartLine` 与 `EndLine` 精准按需切片加载，从而将上下文 Token 消耗降低 80%~95%。

### 7.2 自动化生成工具 (`generate-doc-toc.js`)
脚本路径：`.agents/skills/doc-architect/scripts/generate-doc-toc.js`。
已在 `package.json` 注册快捷命令：
```bash
# 扫描主要规范目录，为缺失目录导航的文档自动注入标准 TOC
pnpm run docs:toc

# 仅检查「目录块是否在场」的文件清单（⚠ 不比对正文标题，见下方「--check 的能力边界」）
pnpm run docs:toc:check

# 对指定文件或目录执行 TOC 注入
node .agents/skills/doc-architect/scripts/generate-doc-toc.js docs/developer/standards/
```

- **`--check` 的能力边界（10-28 现读 `processFile()` 源码逐分支写死，防把"通过"当"已同步"）**：`--check` 只做**两种**判定 —— ① 标题数 ≥ 2 的文档：只判"目录块在不在场"，**块在场即 `return true`，完全不比对块内容与正文标题**；② 标题数 < 2 却仍挂着目录块的文档：报 `[陈旧目录]` 并 `return false`。另注：该分支的进程退出码恒为 0（全脚本只有"未知旗标"与"路径不存在"两处 `process.exit`；10-28 实测：对一个"标题 ≥ 2 且无目录块"的样本，`--check` 打印 `[缺失目录]`、统计行报 `缺失/未加: 1`，**同一命令 rc 仍为 0**），所以**连 rc 都不能当判据**，只准读它打印的行与统计数。⇒ **`--check` 通过 ≠ 目录已同步**：删掉目录块里任意一条条目（正文一字不动），`--check` 依旧报通过。目录面的**权威**判据必须是"正文标题 ↔ 目录条目"的比对尺（本仓长文档的落点见 `workflows/long-doc-landing-and-clean-commit.md` 的结构不变式步与 `workflows/stale-reading-audit.md` 的「结构账」行；两尺须同轮并报），`--check` 只作"块在场"的辅助申报。本条目由账本 `docs/features/ai/text-nsfw-l3-distill-pipeline.md` 第 5 节第 `113` 项的 10-28 代判落地（判者 = Qoder agent（非人类），采信需人类抽查）。
- **工作原理与直接覆盖刷新**：
  1. 预处理剔除围栏代码块与行内代码，防止代码与注释中的 `#` 误识别为标题；
  2. 提取 H1~H5 标题文本（忽略开篇首个文章主标题与目录自身标题）；
  3. 按照 GitHub 标准算法生成锚点 slug，支持中英文混排；
  4. 智能定位文件开篇元数据与导言分割线，或**精准定位已有旧 TOC 区间直接覆盖替换**，彻底杜绝目录残留或行号标题漂移，将最新目录安全注入在前 60 行内。

## 9. 健康度门禁判定口径与已知误报边界 (Health Gate Semantics)

> 目的：`check-doc-health.js` 的判定边界此前只存在于脚本源码里，Agent 撞到「明明不是链接却报死链」时无从判断是文档缺陷还是工具误报。本节固化口径，避免重复排查。

### 9.1 链接扫描的真实剥离层级（`check-doc-health.js` 现读行为）

| 结构 | 是否剥离 | 说明 |
| :--- | :--- | :--- |
| 围栏代码块 ` ``` ` | **已剥离** | `stripFencedCodeBlocks()`，严格 CommonMark 围栏长度栈配对 |
| 行内代码 `` `...` `` | **已剥离**（2026-10-30 新增） | `getInlineCodeRanges()`：等长反引号配对、不跨行，命中位置落在区间内直接跳过 |
| **缩进代码块（4 空格 / Tab）** | **未剥离** | ⚠️ **已知误报源**，见 9.2 |
| 非 `.md` 目标 | 不算死链 | 只计入「源码引用预警」，不影响退出码 |

另注两条易误读的判定顺序：
- **目标文件不存在时不判跨环** —— 跨环判定以「文件存在且为 `.md`」为前提，所以死链不会同时报跨环；修完死链后**可能冒出新跨环**，必须重跑门禁。
- **页内纯锚点 `#x`** 按「源文件自身」解析，校验的是该文件自己的标题集合。

### 9.2 缩进代码块是唯一已知误报：修文档，不要放宽检测器

四空格缩进代码块在 CommonMark 下确实是代码块（GitHub 渲染为代码，不是链接），但检测器不剥离它 ⇒ 块内 `['foo'](a, b)` 这类代码会被误判成链接。

- ✅ **正解**：给该片段补 ``` 围栏（渲染结果完全一致，正文一字不改）。
- ❌ **禁止**：给检测器加「缩进 ≥ 4 空格即视为代码」的宽规则。4 空格同样可能是**嵌套列表的续行缩进**，按空格数判代码会把嵌套列表里的**真实链接**一起吞掉，制造假阴性（门禁变瞎，比误报严重得多）。真要支持，必须引入 CommonMark 容器状态机，属独立议题。

### 9.3 行内代码剥离的实现红线：只许「按区间跳过」，禁止「文本替换」

早期设想的 `content.replace(/`[^`\n]*`/g, ' ')` 方案**会制造新的假阳性**：反引号被抹掉后，原本被隔断的 `[` 与 `](` 会拼接成一条新链接（实测 3 个文件链接计数反而**上升**）。
⇒ 必须先用 `getInlineCodeRanges()` 算出区间，再对 `linkRegex` 的 `match.index` 做 `isInsideRanges()` 判定。

### 9.4 跨环降级的定式（可直接照抄）

保持 `classifyRing()` 不变，把越级直链降级为「显示文本 + 行内代码路径 + 环级标注」：

```markdown
<!-- 改前（L2 文档直连 L4，跨 2 环） -->
- [任务126：快速整理改进](../../archive/tasks/task-126-quick-organize-improvements.md)

<!-- 改后（读者仍拿到路径，拓扑不越级） -->
- 任务126：快速整理改进（`docs/archive/tasks/task-126-quick-organize-improvements.md`，L4 归档）
```

显示文本本身就是文件名/路径时，直接用路径替代，避免同名重复。

### 9.5 锚点重算的两个高频坑

1. **slug 不折叠连续连字符**：标题含 `+` 或 `——` 时，GitHub slug 会产出 `--`（例：`4.38 交付指针更换轮（10-21）—— … 闸门层重评 + 判重尺换代 + 登记同步` → `#438-…重评--判重尺换代--登记同步`）。手写锚点常漏这一个字符，且报错信息看起来像「章节不存在」。
2. **`pnpm run docs:toc` 只重建目录块，不修正文手写锚点**。正文里的 `[§x](#anchor)` 属于手写内容，TOC 工具不会碰，必须按目标文档**实际标题**重算。
