# 移交代码审查参考手册 (REFERENCE)

本手册详细规范了生成代码审查数据包时的双模架构（`--blind` 对内盲审 vs `--external` 对外移交）、文档溯源寻址方法、三轨制审查原则（主线严审 + 超纲建议 + 升维更优解探讨），以及标准提示词模版。

---

## 一、三轨制审查原则：主线严审 vs 开放建议 vs 升维更优范式探讨 (Tri-Track Review)

在代码审查中，生成的 Review 提示词必须贯彻**“三轨制审查原则”**，防止审查者陷入微观行级代码的局部最优陷阱：

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                                   审查者的三条正规通道                                 │
├──────────────────────────┬─────────────────────────────┬───────────────────────────────┤
│ 轨道 A：主线质量与契约   │ 轨道 B：高性价比超纲建议    │ 轨道 C：升维更优范式探讨      │
│ (In-Scope Defect Radar)  │ (Value-Add Gem)             │ (Alternative Paradigm)        │
├──────────────────────────┼─────────────────────────────┼───────────────────────────────┤
│ • 关注点：正确性、边界   │ • 关注点：超出本次范围但具  │ • 关注点：跳出当前代码实现的  │
│   鲁棒性、并发竞态、契约 │   极高商业/架构价值或极低   │   既定思维定势，站到全局与第  │
│   兼容与安全风险         │   改造成本的“低挂果实”      │   一性原理审视根本性更优解    │
│ • 判定：指出具体代码行、 │ • 必须标注：显式打上【超纲  │ • 必须输出：高维视角切入点、  │
│   真实事实与物理破坏半径 │   建议】标签并说明 ROI      │   与当前实现对比矩阵、重构建议│
│ • 目标：必须修复，保底线 │ • 目标：低成本撬动高收益    │ • 目标：破除局部最优，架构跃迁│
└──────────────────────────┴─────────────────────────────┴───────────────────────────────┘
```

## 二、文档寻址与溯源机制 (Docs Sourcing)

为了让第三方审查者拥有充沛的背景输入，无需瞎猜盲人摸象，提示词中**必须完整链接相关的 PRD、Issue 与架构文档**：

| 文档类型 | 检索与提取途径 | 提示词中的呈现形式 |
| :--- | :--- | :--- |
| **Issue 链接 / 编号** | 当前分支关联的 GitHub Issue 编号（如 `#655`）、提交信息前缀或会话讨论中提及的任务单号 | 提供直达链接或编号：`[Issue #655: 数据库三阶段演进规范](https://github.com/.../issues/655)` |
| **PRD / 规格说明书 (Spec)** | `docs/specs/`、`docs/prd/`、`docs/features/` 目录下的相关规范 Markdown 文件 | 给出相对路径与标题：`[PRD-0055: 长效代理人防枚举安全架构](docs/specs/prd-0055.md)` |
| **架构决策记录 (ADR)** | `docs/adr/` 目录下的决策文件（例如 `ADR-0037`、`ADR-0045`） | 给出具体决策编号：`[ADR-0045: 标签源与置信度策略](docs/adr/0045-tag-provenance.md)` |
| **全局领域模型** | 根目录 `CONTEXT.md`、`CONTEXT-MAP.md`、[AGENTS.md](../../../AGENTS.md) | 标明相关章节：`CONTEXT.md「持久化拓扑」章节` |

## 三、免算力原则：为何禁止冗余 Diff 分析？

AI Agent 在整个对话过程中，已经完整见证了代码从无到有的编写、重构与测试过程。会话上下文已经具备了最深刻的改动理解：
- **禁止执行昂贵且重复的 raw git diff 抽取与文本解析**；
- **直接从会话短期/长期记忆中提取**：
  - 为什么这么改？
  - 改了哪几个关键文件？
  - 核心设计权衡是什么？
  - 遇到过什么分歧？
这不仅大幅节约了模型算力和 Token，而且比机器冷冰冰提取出来的 diff 具有高得多的语义信息量！

## 四、对内 `--blind` 紧凑盲审包规范 (Internal Blind Review Spec)

在 `implement-loop` 内部驱动子 Agent 盲审时，生成的盲审包必须遵循以下硬约束：
1. **字符配额限制**：总字数必须严格控制在 **$\le 3,000$ 字符** 内，彻底杜绝注入大文件触发的 CLI 8000 字符崩溃；
2. **零作者辩护偏差**：严禁出现“我之所以妥协是因为...”、“由于时间关系先这么写”等诱导性辩词，只陈述客观 In-Scope 与系统不变量；
3. **注入冻结账本 (Frozen Ledger)**：将上一轮已被 `review-vet` 裁定驳回或固化的设计决策明文写入，阻断子 Agent 提出反向振荡提议；
4. **升维审视强制指令**：明确要求子 Agent 必须从全局架构与第一性原理审视当前代码实现是否陷入局部最优，若有更优架构范式必须显式提出。

## 二、审查原则与纪律
1. **事实为本**：所有缺陷与隐患必须指出具体文件与代码行，并在真实运行调用链中能够成立；
2. **严防无据加戏**：请勿在主线缺陷中掺杂未曾约定的新功能需求；
3. **欢迎高性价比建设性建议**：我们非常欢迎具有高商业价值或架构演进意义的好点子！如果您发现了此类机会，**请务必显式标注【超纲建议】并简要论证其投入产出比（ROI）**，只要性价比高，我们很乐意采纳！
4. **【升维审视与替代方案探讨】**：不要只做局部代码改动的“行级校对员”！若站到更高系统维度审视，发现当前实现陷入了局部最优（例如用大量复杂代码防御了一个本可通过单向数据流或底层既有基础设施直接消灭的问题），极度欢迎在文末专门输出《升维更优方案探讨 (Alternative Paradigm Proposal)》，阐明为什么新方案更好，并给出对比矩阵与重构建议！
5. **【防假想敌过度防御与转化漏斗破坏】**：严禁脱离实际业务场景做学术型过度工程与假想敌防御！严格以资产真实价值（几十元不可变现单机代币 vs 数千万金融冷钱包）为标尺，严禁假想黑客盲猜 2^256 物理机器码并冒被抓风险用强实名微信盗号；严禁引入脆弱 PKI/HMAC 导致误杀与客诉；严禁为十万分之一的罕见手误在支付到账等核心转化链路强加二次确认弹窗或复杂状态机（偶发手误统一由人工客服后台换绑兜底）。
